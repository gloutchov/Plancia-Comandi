### 1. Modello operativo e confini

Plancia Comandi è un terminale desktop per un utente locale. Il processo main gestisce shell, PTY, configurazione, notifiche e operazioni native; il renderer visualizza i terminali e chiede operazioni attraverso un preload dedicato. La logica euristica degli stati è separata dalle operazioni privilegiate.

```text
Utente -> Renderer React/xterm -> API preload -> IPC -> Main Electron
                                                        |-> Shell / PTY -> programmi, file, rete
                                                        |-> settings.json
                                                        |-> notifiche / selettore cartelle / browser
PTY -> parser titoli + schermo headless -> rilevamento stati -> Renderer
```

La shell è un confine di fiducia essenziale: esegue comandi con i permessi del processo app. Non esiste confinamento del terminale a una root workspace, controllo delle cancellazioni o modalità read-only/confirm/full-auto imposta da Plancia Comandi. Il sandbox del renderer non limita i comandi avviati tramite PTY. L'app non è un servizio remoto multiutente e non fornisce autenticazione o controllo remoto.

File di riferimento: [main](electron/main.ts), [preload](electron/preload.ts), [sessioni](electron/sessions.ts), [stati](src/shared/status.ts).

### 2. Segreti, AI e rete

- Non ci sono provider AI, client API AI, gestione di API key, keychain o campi credenziali integrati. L'app non invia autonomamente il terminale a un modello.
- Una CLI avviata può accedere a file e credenziali ed effettuare chiamate esterne. Il suo consenso, la sua autenticazione e le sue policy sono indipendenti dall'app. L'app non intercetta né approva le richieste API dei processi figli.
- Le shell ereditano quasi tutte le variabili del processo, escluso `ELECTRON_RUN_AS_NODE`; vengono impostate variabili di terminale e un fallback di lingua. Variabili sensibili già presenti possono quindi arrivare ai processi figli.
- Il runtime applicativo non implementa telemetria, upload di output o un backend remoto. I link HTTP e HTTPS cliccati vengono aperti nel browser esterno dopo il controllo del protocollo; HTTP resta ammesso. Non c'è una allowlist di host.
- In sviluppo Vite ascolta su `127.0.0.1:47231`, con porta fissa. Non esporre quel server su una rete non fidata. Installazione e packaging possono scaricare dipendenze e strumenti; non sono operazioni offline.
- Non c'è una policy di timeout o TLS applicata alle connessioni dei programmi nel terminale. L'app non configura un bypass TLS nei suoi sorgenti, ma non governa la rete delle shell.

Non inserire segreti in JSON, esempi, log o repository. Per una futura integrazione AI serviranno storage protetto, consenso esplicito per contenuti utente e consenso separato per memoria o contenuti di progetto, provider configurabili, timeout, cancellazione e redazione, con test dedicati. Questi controlli non sono implementati perché tale integrazione non esiste.

**M32, sorgenti 0.3.14 — rilevamento dei processi.** `ChildProcessPoller` mantiene un solo snapshot condiviso per le sessioni vive, comprese quelle nascoste; sessioni terminate o in chiusura non lo richiedono. Senza sessioni vive non resta un timer di polling e il comando proprio in corso viene annullato con AbortSignal, anche al dispose. Risultati tardivi non aggiornano la UI. Creare nuove sessioni non anticipa la scadenza; dopo una risposta valida si attende `childPolling.intervalMs`, dopo gli errori il backoff raddoppia dal valore iniziale al tetto configurato (default 10/20/40/60 s). Non si sovrappongono interrogazioni. La stessa pianificazione protegge Windows e POSIX; i limiti 8000 ms per PowerShell, 4000 ms per ps e 4 MB per la risposta restano invariati.

Le scadenze usano un orologio monotono, senza essere anticipate dalle correzioni dell’orologio di sistema. Il comando Windows resta statico, senza dati utente interpolati, con `-NoProfile`, `-NonInteractive`, [errori terminanti](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_commonparameters?view=powershell-5.1) e nessun cambiamento di execution policy. Snapshot vuoti, righe non numeriche o identificatori fuori dagli interi sicuri sono errori, non prove dell’assenza di figli. La query richiede solo `ParentProcessId` (oltre alle proprietà chiave aggiunte da CIM), senza richiedere nomi o righe di comando: [selezione delle proprietà](https://learn.microsoft.com/en-us/powershell/module/cimcmdlets/get-ciminstance?view=powershell-5.1). Gli snapshot restano nel main; dopo tre errori consecutivi (default) la UI riceve solo il booleano `processDetectionUnavailable` nel contratto SessionInfo già esistente, senza nuovi canali privilegiati. Output, titolo e terminali continuano a funzionare con il segnale dei processi sconosciuto. Una risposta valida rimuove l’avviso. Errori non annullati passano dal reporter già limitato ai metadati; stderr, contenuti e credenziali non entrano nella UI. I quattro parametri `childPolling` accettano solo numeri finiti, arrotondati e limitati; valori mancanti o di altro tipo usano default, il tetto non scende sotto il backoff iniziale.

Verifiche locali M32: adapter con comandi simulati, timer finti, sessioni/PTY simulate, privacy dell’avviso e recupero; suite 535 riusciti/3 saltati, build e renderer Electron con profili/bridge sintetici, IT/EN, chiaro/scuro e tre dimensioni desktop. Le fixture aggiungono l’avviso solo al proprio bridge esterno: nessun flag o API di prova nel prodotto e nessuna lettura di appunti, shell o credenziali personali. Il passo di smoke aggiunto ai workflow manuali esistenti verifica il renderer prima del packaging, senza nuovi trigger, job o permessi. Il primo lancio della suite nel sandbox era impedito da EPERM sul loopback; la ripetizione con loopback consentito passa. Windows x64 reale/pacchettizzato e PowerShell 5.1/7 richiedono il workflow necessario dopo approvazione del commit. CLM su Windows 11 non provata; AppLocker resta un limite dichiarato, non viene disabilitato o aggirato.

### 3. Persistenza, logging e privacy

C33/0.3.13 legge solo le lingue preferite dal sistema dopo ready (fallback al locale applicativo e poi `en`); non registra né invia l’elenco o la regione. La lingua valida salvata prevale e solo il valore applicativo `it`/`en` rimane nelle preferenze. La rinomina dell’eseguibile/bundle conserva `appId` e `app.setName`, quindi non richiede migrazione o cancellazione di `settings.json`. L’ICO Windows è una risorsa statica ufficiale nell’ASAR. Le sonde di primo avvio sono esterne su gemelli e profili sintetici, senza nuovi flag, IPC, accessi di rete o permessi del prodotto. Il harness fuse limita la pulizia al percorso assoluto dell’eseguibile di prova e preserva i PID presenti alla prima verifica: non termina app omonime altrove. La sonda di upgrade Windows è bloccata fuori dai runner GitHub ospitati, rifiuta installazioni/preferenze preesistenti e scarica via HTTPS il solo installer pubblico 0.3.1, verificandone il digest SHA-256 prima dell’esecuzione. Usa registro e profilo sintetici dell’ambiente effimero e conserva le preferenze anche dopo la rimozione.

| Dato / superficie | Comportamento attuale |
| --- | --- |
| Preferenze | JSON non cifrato in `app.getPath('userData')/settings.json`: lingua, tema, vista, font, avvisi, ultima shell/cartella e rilevamento. Non è uno storage segreti. |
| Migrazione | Se manca il file attuale, legge entro il limite il JSON da `Molo`/`molo`, normalizza i campi e salva atomicamente; l’originale resta intatto. Un legacy corrotto entro il limite viene copiato in `.bak` nel profilo nuovo; un legacy eccessivo/non leggibile resta dov’è e blocca le scritture della sessione. |
| Sessioni e output | Stato, nomi, titoli e backlog in memoria; nessun ripristino persistente gestito dall'app dopo l'uscita. Il renderer contiene output visibile e scrollback. |
| Shell e programmi | Possono salvare cronologie, credenziali, file e log indipendentemente dall'app. |
| Diagnostica | `reportDiagnostic` salva in locale solo timestamp, evento statico, codice/operazione ammessi. `diagnostics.jsonl` più `.1`, massimo `diagnostics.maxBytes` per file generato (default 65536, 4096–1048576). Niente messaggi grezzi, stack, percorsi, ambiente o contenuti. Se il file non è scrivibile, stessi metadati su console. Nessun upload e nessun lettore log IPC. |
| Notifiche | Titolo dello stato e nome sessione al sistema operativo; possono comparire fuori dalla finestra, anche sullo schermo bloccato secondo le impostazioni OS. |
| Clipboard | Copia e incolla passano dal modulo `clipboard` del processo main. Il testo non è redatto né mostrato in anteprima. Un'immagine accettata viene scritta come PNG sotto la cartella dati utente e nel terminale viene incollato solo il percorso quotato. |
| Immagini temporanee | Directory e prefisso arrivano da `config/app.config.json`, validati come un solo tratto di percorso. Il nome del file è generato nel main. Scrittura su file temporaneo e poi rinomina. Su Unix la cartella è `0700` e il file `0600`; su Windows valgono i permessi della cartella dati, perché i bit POSIX non sono un confine affidabile. Età e numero massimo eliminano i file generati che corrispondono al prefisso. Gli altri file nella cartella non vengono toccati. |
| Schermate demo | `PLANCIA_SHOT_DIR`/alias legacy scrive PNG della finestra nel percorso indicato. La cattura può includere dati visibili e modifica il tema persistente. |

Le preferenze del sito sono due valori di `localStorage`, `plancia-site.locale` e `plancia-site.theme`, limitati a IT/EN e sistema/chiaro/scuro. Non contengono credenziali o contenuti dei terminali e non cambiano `settings.json`. Valori non ammessi sono ignorati; lo storage bloccato mantiene i comandi funzionanti senza persistenza. `?lang=it|en` seleziona la lingua della visita. I testi del dizionario sono inseriti con `textContent`, senza HTML da input esterni.

**C8 — preferenze e diagnostica, release 0.3.6 verificata.** [settingsFile](electron/settingsFile.ts) limita il file prima della lettura JSON/UTF-8: `settings.maxBytes` 262144 byte, intervallo 16384–1048576; lettura limitata a massimo+1 anche se il file cresce dopo lo stat. UTF-8 invalido, JSON invalido e radici non oggetto richiedono recupero. I nuovi limiti di preferenze/log accettano solo numeri finiti, arrotondati e limitati; gli altri tipi ricevono i default. Campi sconosciuti non vengono ripersistiti, neppure dentro `status`; valori numerici corrotti non causano coercizioni di oggetti.

[privateFile](electron/privateFile.ts) crea un temporaneo esclusivo `settings.json.tmp-<UUID>` nella stessa directory, scrive, esegue fsync e sostituisce con rename; non elimina prima la configurazione valida. Le eccezioni precedenti alla sostituzione lasciano il file precedente intatto; in memoria le modifiche restano utilizzabili con avviso. I temporanei incompleti della chiamata sono rimossi; una terminazione improvvisa può lasciarne uno, ignorato al riavvio. Non è eseguito fsync della directory: non si promette durabilità dopo guasti di alimentazione/filesystem.

Prima dei default, un file corrente non valido/eccessivo viene spostato in `settings.json.bak`, con prenotazione esclusiva del nome; se esiste, viene scelto un altro nome univoco `.bak`. Nessun backup precedente viene sostituito. Lo spostamento non legge/copia file eccessivi in memoria. Se lettura o backup falliscono, il file non viene sovrascritto e le modifiche restano solo in memoria fino al riavvio. I file regolari sono obbligatori; link simbolici sul file sono rifiutati. Nuovi file `0600`, nuove directory `0700` su Unix; su Windows valgono le ACL. `O_NOFOLLOW` non è disponibile su Windows: si applicano controlli lstat e la fiducia nella cartella profilo, non una promessa di protezione da un attaccante dello stesso utente. Dettagli delle API: [filesystem Node.js](https://nodejs.org/docs/latest-v24.x/api/fs.html). Backup senza cancellazione automatica; possono contenere percorsi e pattern privati, quindi non sono artifact pubblici.

[diagnostics](electron/diagnostics.ts) riceve l’errore solo nel main e ne conserva una proiezione consentita, non il testo libero. Per PC-13, lo spawn PTY restituisce il solo codice `pty-spawn-failed`; la UI traduce i codici conosciuti e usa un messaggio generico per ogni altro valore. I gestori IPC precedenti a M1 intercettano errori sincroni e Promise rifiutate prima che Electron ne serializzi il messaggio; restano invariati mittente e validazione dei payload. Moduli PTY/schermo, scritture/resize, polling, preload e avvio usano lo stesso reporter. I codici sconosciuti diventano `UNKNOWN`: si rinuncia al messaggio originale per evitare divulgazioni. Solo fuori dal pacchetto, con `PLANCIA_DIAG_STARTUP=1` una traccia separata, spenta nel funzionamento normale, scrive `startup.jsonl` in `PLANCIA_DIAG_DIR`: percorsi visti all'avvio, con la home e il nome utente sotto `Users` sostituiti: la traccia contiene ancora percorsi locali e va riletta prima di condividerla, ed è un limite della sola traccia di sviluppo sulle variabili `PLANCIA_DIAG_STARTUP` e `PLANCIA_DIAG_DIR`. Se l'avvio fallisce, nome, messaggio, stack, `cause` (null se assente) e `code` (`UNKNOWN` se l'eccezione non ne ha uno), con un tetto di byte. I gestori `uncaughtException` e `unhandledRejection` esistono solo con quella variabile e registrano `name`, `code` e `syscall` quando sono stringhe, un `message` di al massimo 200 caratteri in cui home e percorsi assoluti sono segnaposto, e fino a 8 frame ridotti a funzione e `file:riga`, senza percorsi completi. Residuo noto: in un percorso POSIX con spazi che non è la home, per esempio `/Users/mario rossi/x`, la parola dopo lo spazio resta in chiaro. Non entra in `diagnostics.jsonl` e non esce dal computer. Lo smoke `release` su Windows elenca i listener con `netstat -ano` filtrato sul pid del processo: nella run `43904459587` `Get-NetTCPConnection` non ha restituito testo (`listeners: unavailable`), quindi quel controllo non aveva visto gli indirizzi. Il collegamento TCP a `127.0.0.1` resta il controllo del CDP e rifiuta un listener su `0.0.0.0`, `::` o `*`. Log dell’app limitati e senza contenuti; output/diagnostica di shell, dipendenze ed Electron/OS non sono redatti da questo filtro. Nessuna nuova rete, credenziale o raccolta di output.

Non è configurato un servizio di invio crash report nei sorgenti. Questo non esclude cache o diagnostica ordinaria di Electron/sistema operativo. Prima di condividere log, schermate o configurazioni controllare manualmente contenuti, nomi e percorsi.

Le catture documentali di M3 usano HOME, appData e userData temporanei impostati da un lanciatore di prova prima del caricamento del main, ambiente filtrato e un terminale dimostrativo generato su PTY nativa. Non avviano shell utente, CLI AI né letture degli appunti. I PNG sono catture reali del renderer di produzione, senza ritocchi; provenienza e SHA-256 sono in [capture.json](docs/screenshots/capture.json).

**C28, release 0.3.10 verificata.** Il renderer conserva una sola istanza xterm e una sola sottoscrizione per ciascuna delle massimo 12 sessioni, comprese quelle nascoste; sono rilasciate alla chiusura della sessione. [startupFailure](electron/startupFailure.ts) mostra solo testo IT/EN statico e `STARTUP_FAILED`, duplica su stderr la proiezione consentita di `diagnosticEntry` ed esce con codice 1 dopo aver disposto le sessioni. La lingua viene dalle preferenze caricate, altrimenti è italiana. Questo copre gli errori gestiti di avvio/caricamento, non promette di intercettare errori nativi prima del main. Gli smoke usano sonde esterne sul gemello; nessun bypass o canale privilegiato è aggiunto al prodotto. Il rischio del CDP passato da riga di comando resta distinto da queste variabili.

In [electron/main.ts](electron/main.ts) sono impostati **`contextIsolation: true`**, **`nodeIntegration: false`** e **`sandbox: true`**. Il preload espone metodi specifici, non l'oggetto `ipcRenderer` generico. PTY, filesystem di configurazione e API native rimangono nel main.

M9 nei sorgenti 0.3.7 centralizza il mittente in [ipcSender](src/shared/ipcSender.ts): identità WebContents, frame uguale a mainFrame e URL esatto del documento, con solo il frammento facoltativo. Non basta l’origine `file:` condivisa da file diversi. URL con credenziali, query inattese, documenti diversi, sottoframe e frame mancanti/eliminati sono rifiutati. Il controllo precede gli effetti su tutti i 16 canali in ingresso, inclusi clipboard ed editing; i canali clipboard senza payload rifiutano argomenti extra. La verifica segue le [indicazioni Electron sui mittenti IPC](https://www.electronjs.org/docs/latest/tutorial/security#17-validate-the-sender-of-all-ipc-messages).

[permissions](electron/permissions.ts) installa `setPermissionCheckHandler` e `setPermissionRequestHandler` prima del renderer: il primo restituisce sempre false e il secondo chiama una volta callback(false), senza allowlist di permessi. Sono necessarie [entrambe le API Electron](https://www.electronjs.org/docs/latest/api/session#sessetpermissioncheckhandlerhandler). Non è una sandbox delle shell e non elimina le API native controllate del main.

| Canali | Controlli osservabili |
| --- | --- |
| `app:boot`, `sessions:subscribe` | Solo il mittente della finestra dell'app. `app:boot` non accetta argomenti. `sessions:subscribe` accetta solo un id UUID; un id rifiutato non restituisce il backlog. |

La finestra nega le nuove finestre con `setWindowOpenHandler`. `will-navigate` e `will-redirect` sono annullati salvo l'URL già aperto e, in sviluppo, l'origine del server Vite. Il renderer annulla `dragover` e `drop` così un file trascinato non sostituisce la pagina. Il percorso di un file trascinato si ottiene nel preload con `webUtils.getPathForFile` e viene solo quotato e incollato nel terminale.

La policy è costruita in [src/shared/csp.ts](src/shared/csp.ts), nel meta HTML e nell’header aggiunto da `webRequest.onHeadersReceived`. M9 verifica su macOS ARM64/Electron 45.3.2, ZIP e DMG reali, che le risposte `file:` abbiano l’header con `frame-ancestors` e che il browser blocchi eval, script inline, attributi di evento, fetch e un documento iframe. Il meta omette `frame-ancestors`, direttiva valida solo nell’header. Un pacchetto ignora `VITE_DEV_SERVER_URL`; in sviluppo la policy viene allentata solo per il server HTTP di loopback. La vecchia prova manuale Linux/Electron 45.2.3 resta storica. La run Windows `43823173153` sul commit `3c3fb5efef8053df0514b44ef32f85ee723b0077` è verde, portable e app installata compresi; merge, tag e release 0.3.7 restano da approvare.

Produzione: `default-src 'none'`; script solo `'self'`; niente `unsafe-eval`; niente `unsafe-inline` per gli script; `script-src-attr 'none'`; `connect-src 'none'`; immagini solo `'self'`; nessun host remoto e nessun carattere jolly. `style-src-elem` e `style-src-attr` includono `'unsafe-inline'` perché xterm.js 5 disegna con il renderer DOM: scrive tavolozza, font e animazioni del cursore in un elemento `<style>`, e il contrasto di ogni cella con `setAttribute('style', ...)`. Quei valori dipendono dal tema e dalla cella e non possono essere un foglio statico con hash. Le assegnazioni `element.style` usate per il layout non sono una sorgente CSP. Il polyfill modulepreload di Vite è disattivato, così il HTML di produzione non aggiunge uno script inline.

Sviluppo: `script-src` aggiunge `'unsafe-inline'` soltanto per il preambolo inline che `@vitejs/plugin-react` inietta per React Fast Refresh. Non c'è `unsafe-eval`. Vite inietta anche i CSS come elementi `<style>` durante il ricaricamento: l'eccezione di stile sopra lo consente già. `connect-src` è `'self'`, `http://127.0.0.1:47231` e `ws://127.0.0.1:47231`. `script-src-attr` resta `'none'`, quindi i gestori di evento inline restano bloccati.

**Limiti:** la CSP non confina la shell. I canali aggiunti in M1 controllavano già il mittente. Un mittente accettato è il renderer dell'app: CSP e controllo del mittente non impediscono al codice già in esecuzione nella pagina di usare i canali leciti. La validazione non è uno schema completo di ogni messaggio futuro. M7 aggiunge il matching delle regex personalizzate in un worker cancellabile, descritto sotto; scrittura atomica e diagnostica sono implementate da M8 nei sorgenti 0.3.6, con i limiti e le verifiche descritti sopra.

La conferma di chiusura vive nella UI e si applica solo a stati `busy`/`attention`; il main può chiudere direttamente una sessione. L'uscita dall'app termina le PTY senza una conferma complessiva. Un processo discendente che si distacca non è soggetto a una garanzia di terminazione dell'intero albero.

### 5. Input, limiti e filesystem

**M37 unificata, sorgenti 0.3.16 — budget e prebuild macOS.** I gruppi `sessions` e `processSnapshot` accettano solo numeri finiti, arrotondati e limitati; campi mancanti o di tipo errato ricevono default. La ritenzione del backlog non supera mai la soglia, anche con campo mancante. Il manager usa i valori validati per cap sessioni/capacità del matcher, timer e storico; l’adapter applica i timeout ai comandi di snapshot già statici e cancellabili. Il solo cap pubblico è aggiunto al boot esistente per il messaggio IT/EN: nessun nuovo canale o comando privilegiato. Default 12 sessioni, soglia/ritenzione 300000/250000, timer 400 ms e timeout 4/8 s conservati. Aumentare i limiti può aumentare memoria e lavoro; non sono un tetto globale a memoria o output live.

Il postinstall macOS controlla file regolari Mach-O per l’architettura corrente e carica proprio la prebuild nel solo Electron di sviluppo in un processo Node separato: timeout 5 s, output massimo 4 KiB, codice statico e percorso come argomento, ambiente limitato a PATH/TMP e `ELECTRON_RUN_AS_NODE=1`. NODE_OPTIONS, NODE_PATH, DYLD e altri dati d’ambiente non passano alla sonda; non parte il main applicativo né una shell/profilo personale. Dopo successo, soltanto il suo `spawn-helper` regolare riceve i bit di esecuzione mancanti tramite descrittore senza symlink; il pacchetto node-pty 1.1.0 lo fornisce a 0644. Qualunque assenza, incompatibilità, errore di caricamento/permessi o timeout mantiene il rebuild. Windows conserva le tre prebuild; Linux e `npm run rebuild` conservano la compilazione. Non cambiano fuse, firma, rete o dipendenze. Il controllo si fida della dipendenza locale installata: non è una verifica di provenienza contro un checkout compromesso. Non si usa sui binari distribuiti con fuse chiusi.

**M36/0.3.15 — conferma multilinea.** Il renderer applica lo stesso controllo ad appunti (scorciatoia, Modifica, menu contestuale e evento nativo) e testo trascinato. La decisione riguarda il testo già limitato: LF o CR richiedono conferma se `term.modes.bracketedPasteMode` non è attivo o `ignoreBracketedPasteMode` lo disabilita. Xterm mantiene normalizzazione e marcatori; i percorsi quotati e i limiti esistenti sono conservati. Una sola richiesta è ammessa: la UI riceve solo l’ID della sessione, senza anteprima del testo. Il testo resta in una closure locale volatile fino alla decisione, senza nuovi log, storage, rete o canali privilegiati. Annullamento, chiusura del destinatario, altri dialoghi e smontaggio invalidano la richiesta e le letture tardive; l’invio conserva il destinatario originario e verifica che sia ancora disponibile. Il focus resta nel dialogo con Annulla iniziale. La gestione Modifica risponde subito al protocollo esistente e rinvia la lettura degli appunti al giro successivo, prima di attendere l’utente: il timeout di fallback del main non deve produrre un secondo incolla. L’evento paste nativo è intercettato prima del gestore xterm per impedire un percorso diretto senza conferma. Questo controllo del renderer non aggiunge un confine contro un renderer compromesso; IPC e permessi delle shell restano quelli descritti qui.

**C7 — pattern con budget, release 0.3.5 verificata.** [CustomPatternMatcher](electron/customPatterns.ts) conserva un solo worker, una richiesta attiva e al massimo una schermata pendente per sessione (12 sessioni). La coda sostituisce le schermate superate; i risultati sono accettati soltanto per il testo e la revisione correnti. I pattern compilati sono riusati nel worker. Le regole integrate restano nel rilevatore puro e non costruiscono regex da stringhe utente. [customPatternText](src/shared/customPatternText.ts) limita la copia prima della rimozione ANSI: ultima riga non vuota per idle, ultime 10/12 righe per busy/attention. Il limite riduce il contesto dei pattern molto lunghi: lo stato resta una stima, non una protezione per i comandi.

Il timer della richiesta vive nel main, separato dal matching. Decorrono al massimo 50 ms dalla disponibilità del worker per compilazione/matching di una richiesta; l’avvio ha una scadenza separata di 2000 ms. La terminazione è asincrona e una sostituzione attende la sua conclusione, secondo le [API Node](https://nodejs.org/docs/latest-v24.x/api/worker_threads.html#workerterminate). È un budget applicativo soggetto alla pianificazione del sistema, non una garanzia di tempo reale. Timeout o errore sospendono tutte le liste del profilo fino a cambiamento delle liste o riavvio, evitando tentativi continui. Cambiare solo tempi, lingua o tema non riattiva un profilo sospeso. Regex sintatticamente errate vengono ignorate e segnalate; i pattern validi del profilo continuano a funzionare. Chiusura, uscita della PTY, svuotamento delle liste e `dispose` cancellano i lavori pertinenti e rilasciano le risorse; chiudere una sessione non cancella quelle delle altre.

I quattro parametri centrali sono `budgetMs` (50, 10–250), `startupTimeoutMs` (2000, 500–10000), `maxInputChars` (4096, 256–32768) e `workerMemoryMb` (32, 16–128). L’ultimo limita la old-generation JavaScript, non l’intero RSS o le allocazioni native. Il worker ha `env: {}` e `execArgv: []`, riceve solo le tre porzioni di schermo e i pattern limitati: non vengono inviati separatamente metadati cwd/titolo, variabili d’ambiente o il backlog completo. Il testo visibile può comunque contenere percorsi, segreti o altri dati sensibili già presenti nel terminale e viene copiato soltanto in questo worker locale. Restituisce booleani e codici fissi; gli avvisi di matching non ripetono pattern, output o errori grezzi. Cache e copie sono locali e volatili. Non sono introdotti rete, segreti, storage o nuovi canali IPC: il codice di avviso viaggia con i metadati delle sessioni.

Il [programma worker](electron/customPatternWorker.ts) è un testo statico fidato incluso nel bundle main, avviato con `eval: true` per funzionare anche da ASAR senza nuovi file eseguibili. Non vi si interpola alcun dato utente; le stringhe ricevute sono argomenti di `RegExp`, mai codice JavaScript da eseguire. Non cambia la CSP del renderer e non viene aggiunto `unsafe-eval`. Il worker conserva le capacità Node del processo: isola il calcolo, non costituisce un sandbox di sicurezza né un limite globale alla memoria dell’app. Anche runtime, sistema e dipendenze rimangono superfici fidate.

### 1. Operating model and boundaries

Plancia Comandi is a desktop terminal for a local user. The main process manages shells, PTYs, configuration, notifications and native operations; the renderer displays terminals and requests operations through a dedicated preload. Heuristic status logic is separate from privileged operations.

```text
User -> React/xterm renderer -> preload API -> IPC -> Electron main
                                                      |-> Shell / PTY -> programs, files, network
                                                      |-> settings.json
                                                      |-> notifications / folder picker / browser
PTY -> title parser + headless screen -> status detection -> Renderer
```

The shell is a key trust boundary: commands run with the app process's permissions. Plancia Comandi imposes no terminal workspace root, deletion checks or read-only/confirm/full-auto modes. The renderer sandbox does not restrict commands launched through the PTY. The app is not a remote multiuser service and provides no authentication or remote control.

Source references: [main](electron/main.ts), [preload](electron/preload.ts), [sessions](electron/sessions.ts), [status](src/shared/status.ts).

### 2. Secrets, AI and networking

- There are no integrated AI providers, AI API clients, API-key management, keychain or credential fields. The app does not independently send terminal content to a model.
- A launched CLI may access files and credentials and make external calls. Its consent, authentication and policies are independent of this app. The app neither intercepts nor approves child-process API requests.
- Shells inherit almost all process variables except `ELECTRON_RUN_AS_NODE`; terminal variables and a locale fallback are set. Existing sensitive variables can therefore reach child processes.
- The app runtime implements no telemetry, output upload or remote backend. Clicked HTTP and HTTPS links open in the external browser after a protocol check; HTTP remains allowed. There is no host allowlist.
- In development Vite listens on `127.0.0.1:47231`, a fixed port. Do not expose it to an untrusted network. Installation and packaging may download dependencies and tools; they are not offline operations.
- No timeout or TLS policy is applied to connections made by terminal programs. The app source does not configure a TLS bypass, but it does not control shell networking.

Do not place secrets in JSON, examples, logs or the repository. A future AI integration would require protected storage, explicit consent for user content and separate consent for memory or project content, configurable providers, timeouts, cancellation and redaction, with dedicated tests. These controls are not implemented because that integration does not exist.

### 3. Persistence, logging and privacy

C33/0.3.13 reads only preferred system languages after ready (falling back to the application locale and then `en`); it neither logs nor sends the list or region. A valid saved language takes precedence, and only the app value `it`/`en` remains in preferences. Renaming the executable/bundle preserves `appId` and `app.setName`, requiring no migration or deletion of `settings.json`. The Windows ICO is an official static ASAR resource. First-launch probes are external on twins and synthetic profiles, adding no product flags, IPC, network access or permissions. The fuse harness scopes cleanup to the absolute probe executable path and preserves PIDs present at its first check: it does not terminate same-named apps elsewhere. The Windows upgrade probe is blocked outside GitHub-hosted runners, refuses preexisting installations/preferences and downloads only the public 0.3.1 installer over HTTPS, verifying its SHA-256 digest before execution. It uses the disposable environment’s synthetic registry/profile and preserves preferences after removal too.

| Data / surface | Current behavior |
| --- | --- |
| Preferences | Unencrypted JSON in `app.getPath('userData')/settings.json`: language, theme, layout, font, alerts, last shell/folder and detection. This is not secret storage. |
| Migration | If the current file is missing, reads bounded JSON from `Molo`/`molo`, normalizes fields and saves atomically; the original remains intact. A corrupt legacy file within the limit is copied to `.bak` in the new profile; an oversized/unreadable legacy file stays in place and blocks session writes. |
| Sessions and output | State, names, titles and backlog in memory; no app-managed persistent restoration after quitting. The renderer contains visible output and scrollback. |
| Shells and programs | May save history, credentials, files and logs independently of the app. |
| Diagnostics | `reportDiagnostic` stores only timestamp, static event and allowlisted code/operation locally. `diagnostics.jsonl` plus `.1`, at most `diagnostics.maxBytes` per generated file (default 65536, 4096–1048576). No raw messages, stacks, paths, environment or contents. If the file is unwritable, the same metadata goes to the console. No upload or IPC log reader. |
| Notifications | State title and session name sent to the OS; may appear outside the window, including on a locked screen depending on OS settings. |
| Clipboard | Copy and paste go through the main-process `clipboard` module. Text is not redacted or previewed. An accepted image is written as a PNG under the user-data directory and only its quoted path is pasted into the terminal. |
| Temporary images | Directory and prefix come from `config/app.config.json` and are validated as a single path segment. The file name is generated in main. The write uses a temporary file and then a rename. On Unix the directory is `0700` and the file `0600`; on Windows the user-data directory ACL is the boundary, because POSIX mode bits are not a reliable boundary there. | Demo screenshots | `PLANCIA_SHOT_DIR`/legacy alias writes window PNGs to the specified path. Capture can include visible data and changes the persistent theme. |

Site preferences are two `localStorage` values, `plancia-site.locale` and `plancia-site.theme`, restricted to IT/EN and system/light/dark. They contain no credentials or terminal content and do not change `settings.json`. Unsupported values are ignored; blocked storage keeps controls working without persistence. `?lang=it|en` selects the visit's language. Dictionary text is inserted with `textContent`, with no HTML from external input.

**C8 — preferences and diagnostics, verified release 0.3.6.** [settingsFile](electron/settingsFile.ts) bounds the file before JSON/UTF-8 reading: `settings.maxBytes` 262144 bytes, range 16384–1048576; reading is limited to maximum+1 even if the file grows after stat. Invalid UTF-8, invalid JSON and non-object roots require recovery. New preference/log limits accept only finite numbers, rounded and clamped; other types receive defaults. Unknown fields are not persisted again, including inside `status`; corrupt numeric values cannot trigger object coercion.

[privateFile](electron/privateFile.ts) creates an exclusive `settings.json.tmp-<UUID>` in the same directory, writes, fsyncs and replaces using rename; it never deletes the valid configuration first. Exceptions before replacement leave the old file intact; in-memory changes remain usable with a warning. Incomplete temporary files from the call are removed; abrupt termination can leave one behind, ignored at restart. The directory is not fsynced: durability after power/filesystem failure is not promised.

Before defaults, an invalid/oversized current file is moved to `settings.json.bak`, with exclusive name reservation; if it exists, another unique `.bak` name is used. Older backups are never replaced. Moving avoids reading/copying oversized files into memory. If reading or backup fails, the file is not overwritten and changes remain in memory until restart. Regular files are required; leaf symlinks are refused. New files use Unix `0600`, new directories `0700`; Windows relies on ACLs. `O_NOFOLLOW` is unavailable on Windows: lstat checks and a trusted profile directory apply, without claiming protection from a same-user attacker. API details: [Node.js filesystem](https://nodejs.org/docs/latest-v24.x/api/fs.html). Backups are not automatically deleted; they may contain private paths and patterns and must not be public artifacts.

[diagnostics](electron/diagnostics.ts) receives errors only in main and retains an allowlisted projection rather than free text. For PC-13, PTY spawn returns only `pty-spawn-failed`; UI translates known codes and uses a generic message for all other values. Pre-M1 IPC handlers catch synchronous errors and rejected Promises before Electron serializes their messages; sender and payload validation are unchanged. PTY/screen modules, writes/resizes, polling, preload and startup use the same reporter. Unknown codes become `UNKNOWN`: the original message is discarded to avoid disclosure. Only outside a package, with `PLANCIA_DIAG_STARTUP=1` a separate trace, off in normal use, writes `startup.jsonl` in `PLANCIA_DIAG_DIR`: the paths seen at startup, with the home directory and the user name under `Users` replaced: the trace still contains local paths and must be re-read before sharing, which is a development-trace limitation on the `PLANCIA_DIAG_STARTUP` and `PLANCIA_DIAG_DIR` variables. If startup fails, the exception name, message, stack, `cause` (null when absent) and `code` (`UNKNOWN` when the exception has none), with a byte cap. The `uncaughtException` and `unhandledRejection` handlers exist only with that variable and record `name`, `code` and `syscall` when they are strings, a `message` of at most 200 characters in which home and absolute paths are placeholders, and up to 8 frames reduced to function and `file:line`, without full paths. Known residue: in a POSIX path with spaces that is not the home directory, for example `/Users/mario rossi/x`, the word after the space stays in clear text. It does not enter `diagnostics.jsonl` and it does not leave the computer. Windows `release` smoke lists listeners with `netstat -ano` filtered to the process pid: in run `43904459587` `Get-NetTCPConnection` returned no text (`listeners: unavailable`), so that check had not seen the addresses. The TCP connection to `127.0.0.1` remains the CDP check and rejects a listener on `0.0.0.0`, `::` or `*`. App logs are bounded and content-free; shell, dependency and Electron/OS output/diagnostics are not redacted by this filter. No new network use, credential handling or output collection.

No crash-report upload service is configured in the source. This does not exclude ordinary Electron/OS caches or diagnostics. Manually check content, names and paths before sharing logs, screenshots or settings.
